# 主持决策与制作交接

## 开场：把一句想法变成评审基线

先给出最小可交付范围：玩家能做什么、触发什么结果、哪些内容不在本次开发中。默认聚焦本地模组开发，不添加联机、地图、账号、上架或收益任务。用户提到中国版基岩 1.24 时保留这个目标，不把它改写为已经确定的 ModSDK 版本。

把信息分为已给定事实、可撤销的工作假设、影响实现的未知项。工作假设应具体到“同一目标重复点击时忽略正在播放的对白”，而不是“所有异常都已考虑”。缺少素材时优先选择现有资源和可验证实现，不能默默承诺生成当前流水线不支持的模型或纹理。

## 汇总：维护一份能执行的方案

方案以以下顺序组织，内容不足的栏目可合并：目标与范围；玩家流程；状态和触发规则；参数及单位；实现能力与接口依据；声音资产；制作分工；验收场景；未验证条件。后续汇总保留已接受规则，只改受本轮意见影响的部分。修改参数后同步修改相关示例、声音触发及验收预期。

遇到分歧先定位类型：规则含糊交策划，收益或量纲交数值，接口与生命周期交技术，反例与异常交独立审查，台词与音频资源交调音。不同专业对同一问题有意见时明确一个主问题与参与者，不能将原问题改名成多个新问题。

主持可以整合修复，不能替提出者关闭问题。保留调度器提供的编号；专业角色确认修复后才由程序更新台账。不要将“大家应该同意”当作投票或完成状态。

## 从共识到人工批准

共识的含义是“目前方案可交给人审核”，不是自动授权制作。整理出用户需要审核的范围、模型调用、声音台词、素材缺口与目标版本。没有批准记录时只提交任务建议，不声称已向程序和音效 Agent 下单。

人工批准后的编程任务应包含文件/模块职责、可观察行为、必须保持的不变量和声音事件标识；声音任务包含台词或声响描述、使用场景、长度目标与资源标识。二者引用同一版方案，不能让程序和调音自行改写已批准需求。

## 示例：矿洞向导与宝箱

原需求“向导说欢迎语，打开宝箱有声音”。先定义交互成功时播放欢迎语；重复点击的冷却按该 NPC 实例处理；宝箱仅在关闭→打开成功时播放一次。具体冷却数值由方案确定，声音时长只是创作目标。若程序指出接口未核对，记录相应能力和核验任务；不能将“没有试听”误认为玩法规则永远不能共识。若用户要求的核心播放能力没有证据且没有替代实现，则保留真实技术分歧。

## 停止时交付有用结果

轮次或预算即将耗尽时，保留已经同意的部分，列出最少尚未解决问题、具体影响、负责人和下一步所需证据。不要要求每位成员重写完整方案，也不要降低重大问题等级来凑共识。剩余验收事项进入建议，真正阻止实施的问题继续保留。
