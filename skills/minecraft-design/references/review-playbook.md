# 玩法规格与验收场景

## 需求拆解

把“更有趣”“增加附魔”“NPC 可以对话”拆成可观察行为：入口、前置条件、玩家操作、系统反馈、成功结果和失败结果。明确功能属于新增能力还是修改已有机制，保留用户指定题材。默认只使用已有游戏资源；音效交调音设计，不自动扩展美术或地图需求。

对于物品/附魔，说明适用对象、启用与移除条件、叠加和互斥规则、触发机会、持续时间及显示反馈。对于 NPC，对白必须与交互结果匹配；拒绝交互、冷却中、条件满足的表现分开。对于容器/交互物，区分尝试操作与成功状态变化，避免按点击次数发放奖励或播放成功声。

## 状态表是实现契约

每条状态转换写成“当前状态 + 触发 + 条件 → 新状态 + 副作用”。不要只描述正常路径。只补充与需求相关的失败路径，例如条件不足保持原状态、取消操作释放临时占用、对象被移除后停止后续动作。纯逻辑组件不强加死亡、联机、持久化系统。

示例（示意，非 SDK 接口）：idle + 交互 + 未冷却 → speaking + 请求播放；speaking + 再次交互 → speaking + 忽略；speaking + 结束/失败 → idle + 允许后续交互。若没有可靠播放结束通知，和技术、调音约定保守的固定冷却，不把创作目标时长当作实际文件时长。

## 对齐各专业

给数值提供次数限制、时间定义和希望达到的节奏；允许调整的参数与不可更改的玩法目标分开。给程序提供状态规则与失败反馈，不替程序承诺未验证接口。给调音提供精确台词、触发成功条件、重复播放策略及“哪些动作不要声音”。

技术限制导致范围收缩时，比较保留核心体验的最小替代方案。先说明哪一条体验改变，再修改方案，不能用“后续完善”隐藏核心功能被删掉。

## 可执行验收描述

使用“给定前置状态，执行一个动作，观察结果”的格式。示例：给定NPC处于冷却中，再次交互，预期不新增播放请求且保持原冷却时间。每个核心行为至少有正常场景和一个最相关边界；无需为每个任务填满所有测试类别。

规则已明确可以通过策划评审，后续游戏内体验仍需人工确认。若体验目标只是主观偏好，提出两种可调参数并给建议，不把个人偏好升级为阻断项。

## 易混淆情况

- “唯一奖励”要指明按任务实例还是角色计算，不凭空引入联网防刷。
- “冷却5秒”要指明起点、成功/失败是否消耗以及边界等于5秒的行为。
- “随机掉落”要指明是否每次独立、是否替换抽取、是否保底。
- “物品失效”要指明已有状态如何解除，而不是只禁止新触发。


## 人工确认与开发任务交接

当宿主切换到制作任务单阶段时，遵守该阶段 schema，不继续输出圆桌发言格式。把数值成员的明确结论写进策划：单位、范围、概率、冷却、上限、失败分支与重复触发处理。不要只写“按数值表执行”却不给程序实际参数。分清玩家操作顺序、服务器状态、客户端显示和资源播放时机。

完整策划输入时保留原本已明确的玩法和美术意图，不擅自缩成另一个简单游戏；只有想法时补齐最小可玩循环，把假设明确提交人工审核。美术制作当前仅提供多模态 API 配置入口，有必需新素材必须列为待完成资源；不得通过忽略素材清单绕过交付门槛。声音制作须给实际台词/质感和触发条件，不把 StepFun API 当作游戏运行依赖。

人工提出修改后阅读上轮方案与修改意见，先列受影响项，再在新会议中形成新方案，不能自动沿用旧批准。主管主持新一轮复核；策划保留不受影响的约定，处理数值、程序、美术与音效之间的冲突。审批前不启动生成代码、付费音频或美术调用。制作时间不预估成确定秒数，最终由宿主实际任务状态决定完成。
