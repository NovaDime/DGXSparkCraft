# 比赛演示与证据准备

演示中心是专业 Skills 如何参与多轮模组设计评审：提出一个真实议题，观察不同角色如何发现问题、修改规则并复核。交付方案与会议记录；游戏画面在取得实际可运行成果后作为补充。

## 当前可录制内容

本地默认是**规则模拟，不是 AI 推理**。可以展示界面、角色顺序、分歧台账、重新评审、停止和导出，但录屏与讲解必须保留模拟标识。固定回复仅用于软件流程演练，不能用于证明 Skills 的专业效果或 Spark 的执行能力。

三个示例议题分别关注重复领奖、协作机关恢复和生存挑战结算。优先选“采集委托与重复领奖”，它能以一个具体交互串起策划规则、数值节奏、技术实现和独立逻辑审查。示例是新写的评审输入，未复用旧项目源码或成品方案。

## 接入真实模型后的演示顺序

1. 展示任务目标与约束，确认页面为 OpenClaw 模式，说明实际模型运行位置。
2. 打开一个角色的 Skill，让评委看到它如何定义职责、质疑方法和关闭问题所需证据。
3. 开始真实会议，捕捉一条有实际影响的问题：例如提交物品与发奖之间掉线，原规则如何导致物品丢失或重复领奖。
4. 展示主管据此修改方案，相关角色在下一轮重放反例，并说明关闭或保留该问题的依据。若没有发现问题，保留真实记录，不补录伪造对话。
5. 导出 Markdown 方案与 JSON 会议记录，展示未解决事项、停止原因和关键配置。将完整 trace 留作可核查材料。

视频时长与提交格式按实际比赛要求确定。准备材料时另保留软件提交版本、Skill 文件指纹、目标 OpenClaw 版本、模型配置及运行日期。

按新增的 [Spark 连接与 Skill 交付要求](spark-connection-requirements.md)，随附每个 Skill 的 `SKILL_CARD.json`、配置预检计划、评测场景与实际验收记录。可从 [BENCHMARK 模板](../skills/spark-connect/BENCHMARK.md) 建立报告。卡片、哈希清单、扫描结果、效果评估、数字签名与人工接受分别说明；未签名或未测项目保持相应状态，不把截图中示例的认证与性能写成项目结果。本次不包含美术连接演示。

## 验收分别记录

| 层级 | 需要记录的内容 | 能说明的结果 |
|---|---|---|
| 本地软件验证 | 测试命令与输出、模拟会议导出 | 调度、存储、异常及协议逻辑可用 |
| 真实角色运行 | OpenClaw 记录、角色与 Skill、输入输出 | 实际模型按角色完成评审 |
| Skill 效果 | 具体问题、修改前后差异、开发者复核意见 | 本案例中专业评审是否有用 |
| Spark 资源实测 | 型号、模型、量化、并发、耗时与资源采样 | 对应配置下的实际运行表现 |
| 游戏内验证 | SDK 版本、平台、操作步骤、日志与录屏 | 对应模组场景的实际运行结果 |

测试通过不等于模型方案正确；模型说“已执行”不等于工具实际运行；静态脚本检查不等于游戏内可玩。未做的验证明确列为待验证。存在 SDK 版本、奖励一致性等未解决问题时允许展示待复核结果，不能以达到轮数上限替代共识。

## 材料边界

本次材料只描述从零重写的圆桌与已取得证据。两篇博客作为思路来源，旧项目的成本、内存、迭代轮数等数字不迁移到本项目。十万多份销售数据的对应作品及系统参与情况尚待确认，当前稿件不据此声称本次 Skills 已经过市场验证。

游戏片段需来自实际实现和验证过的模组，并说明 AI 圆桌与人工开发分别完成的部分。原始 trace 保留完整，剪辑可以压缩等待时间，但不得改写意见、隐藏会影响结论的失败或去掉模拟标识。
